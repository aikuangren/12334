# 后端上线改造清单

## 1. 背景与目标

当前项目已经完成抽卡 H5、卡册、卡池、后台基础配置、抽卡概率和埋点验证，但后端仍属于原型验证阶段，核心表现为：

- 使用 H2 内存库，服务重启后数据会重置。
- `spring.jpa.hibernate.ddl-auto=create-drop`，不适合生产数据。
- C 端接口直接信任前端传入的 `userId`。
- `/admin/**` 管理接口暂未接入公司后台权限。
- 存在原型测试接口，例如模拟次日、模拟完课重置、练习加次数。
- 上传资源仍是本地目录方案，未接正式 OSS/CDN 流程。

当前轻量验证目标：

- 不开发后台管理系统。
- 不启用后端 API 服务和 MySQL。
- 卡池、卡牌、概率和资源地址固定在静态 JSON 中。
- H5 从 OSS/CDN 读取页面、静态配置和卡牌资源。
- 卡册、每日次数和抽卡历史临时记录在前端本地存储中。
- 该方案只用于轻量功能验证，不承诺真实用户资产、防刷和跨设备同步。

后续正式化目标：

- 如需要真实用户资产、每日次数防刷、跨设备同步和抽卡历史，再启用轻量 Node.js 服务 + MySQL 5.7。
- Java 服务保留为规则参考和备选方案。
- 启用后端后，抽卡、扣次数、发卡、入卡册需在并发下保持数据一致。

### 1.1 本期确认口径

- 本期只做轻量功能验证，卡册、次数和历史记录在前端本地存储。
- 本期不启用 MySQL，不接后端 API 服务。
- 后续如需要真实用户资产，推荐使用 Node.js + Fastify + MySQL 5.7 的轻量方案；Java 服务不作为当前优先上线方案。
- 因 MySQL 8.0 以上当前存在监听缺陷，后续如启用数据库，不建议启用 MySQL 8.0+。
- 本期不接完课和练习事件，只保留每日免费抽卡次数；次数用完后只能等待第二天重置。
- 抽卡次数规则先固定在静态配置中；后续如启用后台，再扩展为后台配置化。
- 功能上线需要公司审批，遵循公司分支规范、MR、盖娅发布流程。
- 资源上传使用公司 OSS，并遵循 OSS 使用规范与生命周期管理要求。
- 埋点事件名由本项目自行定义。
- 本期暂不接公司登录态和网关校验；埋点按规范携带本地环境信息，由大数据侧基于 cookie 等信息解析用户 ID。业务接口的用户识别仍需保留过渡方案，并记录安全风险。
- 管理后台本期仅个人使用，暂不接 PBM 后台权限；后续多人使用或正式运营前再补权限接入。

## 3. 正式后端架构改造

### 3.1 推荐轻量架构

本期推荐使用 Node.js 轻量服务：

```text
H5 / OSS / CDN
        |
        v
Node.js + Fastify
        |
        v
MySQL 5.7
```

说明：

- H5、图片、音频、视频资源走公司 OSS/CDN。
- 卡池、卡牌、概率、资源地址固定在静态 JSON 中。
- Node.js 服务只提供抽卡、卡册、历史、次数、模拟次日等必要接口。
- MySQL 只保存用户资产和抽卡流水。
- 不开发正式卡牌管理后台。
- Java 服务保留为原型参考，不作为本期优先上线服务。

### 3.2 数据库

说明：

- 公司当前使用 MySQL 与 OSS。
- 本期需要服务端保存次数、卡册和历史，因此需要 MySQL。
- 建议使用公司正式 MySQL 5.7 环境。
- MySQL 8.0 以上当前存在监听缺陷，本期不建议使用 MySQL 8.0+。
- 存储引擎使用 InnoDB，便于行锁和事务一致性控制。

必须完成：

- 生产环境不使用 H2。
- 执行 `node-service/sql/001_init.sql` 建表。
- 数据库账号、密码、连接地址通过环境变量或配置中心注入，不写入代码仓库。

建议表结构：

1. 用户次数表。
2. 用户卡册表。
3. 抽卡订单表。
4. 抽卡订单明细表。

### 3.3 抽卡次数配置

本期只支持每日免费次数。

规则：

- 每个用户每天拥有固定免费抽卡次数。
- 次数用完后不能通过完课或练习补充，只能等待第二天重置。
- 每日重置时间仍按业务日期配置，例如当前原型中的 05:00 切日。
- 免费次数、重置时间、卡池绑定关系本期可固定在静态配置中。
- 如后续需要运营侧调整，再接入后台配置化。

后续扩展：

- 完课重置次数。
- 练习奖励次数。
- 活动额外赠送次数。
- 用户分层或活动分层次数规则。

### 3.4 推荐核心索引

| 表 | 索引 | 说明 |
| --- | --- | --- |
| `user_draw_quota` | unique(`user_id`, `quota_date`) | 用户每日次数唯一 |
| `user_card` | unique(`user_id`, `card_id`) | 防止重复插入同一用户卡 |
| `draw_order` | index(`user_id`, `pool_version`, `created_at`) | 历史记录查询 |
| `draw_order` | unique(`user_id`, `request_id`) | 抽卡请求幂等 |
| `draw_order_card` | index(`order_id`) | 订单卡牌明细查询 |

## 4. 用户身份与权限

### 4.1 C 端用户身份

当前接口：

```http
POST /api/card-draw/draw?userId=10001
```

长期方案不应继续信任前端传入的 `userId`，应从公司登录态、网关 token 或统一用户中心解析用户。

本期方案：

- 暂不接公司登录态和网关校验。
- 业务接口可保留现有 `userId` 过渡方案，需确认 `userId` 来源由 H5 容器、入口链接或公司页面环境注入。
- 埋点按规范携带本地环境信息，由大数据侧基于 cookie 等信息解析用户 ID。
- 不建议在业务代码中主动读取并上报完整 cookie 值，避免泄露登录态或敏感信息。
- 该方案存在用户伪造风险，需在上线评审中明确为本期过渡风险。

后续方案：

- 后端从网关登录态解析用户 ID。
- 后端统一注入当前用户，例如 `CurrentUser user`。
- C 端接口去掉前端 `userId` 参数。
- 所有用户资产查询使用当前登录用户，避免越权查看他人卡册。

### 4.2 后台管理权限

需要保护的接口：

- `/admin/cards/**`
- `/admin/card-draw/**`
- `/admin/resources/**`

本期方案：

- 公司有 PBM 后台可用于后续配置权限。
- 当前管理后台只有个人使用，本期可暂不接 PBM 权限。
- 管理后台访问地址、环境和账号使用范围需要在上线审批中说明。
- 后台操作仍建议保留基础操作日志，方便回溯。

后续上线要求：

- 接入公司后台登录态。
- 区分查看、编辑、上下线、上传、概率配置权限。
- 重要操作记录操作人、操作时间、操作内容。
- 概率配置和卡池上线建议增加二次确认或审批流。

### 4.3 埋点用户识别

本期埋点事件名由项目自行定义。

当前 H5 已按以下结构上报：

```json
{
  "t": "card.000001",
  "v": {
    "action": "PG_CARD_MAIN",
    "unitid": "10007"
  }
}
```

本期要求：

- `t` 固定为 `card.000001`。
- `action` 由项目定义并保持稳定。
- 公共参数中保留 `project`、`page_name`、`unitid`、`userId`、`poolVersion` 等字段。
- SDK 自动携带的本地环境信息和 cookie 信息由大数据侧解析用户 ID。
- 业务代码不主动读取或拼接完整 cookie，避免把登录态敏感内容写入日志或请求参数。
- 后续接网关登录态后，埋点中的用户 ID 与后端解析用户 ID 需要做一致性校验。

## 5. 并发与一致性设计

预估并发量：50 左右。

50 并发本身不高，静态页面和查询接口压力较小。重点风险集中在抽卡写操作：

- 同一用户连续点击抽卡。
- 同一用户多端同时抽卡。
- 同一用户同一张卡重复获得时 `owned_count` 丢失更新。
- 扣次数成功但订单未生成。
- 订单生成成功但卡册未更新。

### 5.1 抽卡事务边界

抽卡接口必须在一个事务内完成：

1. 读取并锁定用户当天次数。
2. 判断可用次数。
3. 扣减 1 次。
4. 计算 5 张卡牌。
5. 创建抽卡订单。
6. 创建订单卡牌明细。
7. 更新用户卡册。
8. 返回抽卡结果。

任何一步失败都应回滚。

### 5.2 扣次数并发策略

推荐使用数据库行锁：

```sql
select * from user_draw_quota
where user_id = ?
  and quota_date = ?
for update;
```

锁住当前用户当天次数记录后再扣减。

也可以使用乐观锁：

- `user_draw_quota` 增加 `version` 字段。
- 更新时带 `where version = ?`。
- 更新失败时重试或返回并发冲突。

对当前业务，行锁更直接，50 并发下足够稳定。

### 5.3 用户卡册更新策略

`user_card(user_id, card_id)` 必须唯一。

建议逻辑：

- 已拥有：使用原子更新 `owned_count = owned_count + 1`。
- 未拥有：插入新记录。
- 插入遇到唯一键冲突时，改为原子更新。

避免两个并发请求同时判断“未拥有”，导致重复插入或其中一次失败。

### 5.4 抽卡幂等

前端每次开包生成一个 `requestId`。

接口示例：

```http
POST /api/card-draw/draw
Content-Type: application/json

{
  "poolVersion": "v1",
  "requestId": "uuid-from-client"
}
```

后端要求：

- `draw_order` 保存 `request_id`。
- 建唯一索引 `user_id + request_id`。
- 如果同一请求重复提交，直接返回第一次抽卡结果。
- 前端重复点击、网络重试、页面误触都不能造成重复扣次数。

## 7. 上传与资源安全

当前上传逻辑主要依赖扩展名判断，生产需要加强：

- 校验文件大小。
- 校验真实 MIME。
- 图片建议做重新编码或安全扫描。
- 禁止上传 HTML、JS、SVG 等可执行或可注入内容。
- 文件名使用随机 UUID，不使用用户原始文件名。
- 上传目录不能允许路径穿越。
- 资源建议上传到公司 OSS，并通过 CDN 访问。
- 本期后台上传接口可暂不接 PBM 鉴权，但需要限制使用环境和访问范围。

公司 OSS 使用规范：

- 需求方需明确使用场景，本项目属于静态文件和普通文件场景。
- Bucket 由 SRE 创建，并根据使用场景添加生命周期管理规则。
- Bucket 命名使用小写英文，推荐格式为“部门简称-业务名称”，不要使用拼音。
- Bucket 需要添加标签信息：Department、Owner、Type。
- 文件不得直接放在根目录。
- 按类型或使用场景创建目录，例如 `image/`、`audio/`、`video/`、`system/`。
- 如果文件按日期递增，建议按月或按天创建目录。
- 服务开通后需要记录到 OSS 生命周期管理台账。

本项目建议目录：

```plaintext
card-draw/
├── image/YYYY/MM/DD/
├── audio/YYYY/MM/DD/
├── video/YYYY/MM/DD/
└── system/
```

生命周期建议：

- 卡牌图片、音频和卡包素材属于业务静态资源，需覆盖活动周期和回溯周期。
- 临时上传、未绑定卡牌的素材可设置较短生命周期。
- 碎片清理建议参考公司规范设置 30 天或更短。
- 具体低频、归档、删除周期由 SRE 按使用场景配置并审批。

## 8. 分支规范与上线流程

本项目上线遵循公司分支规范与上线审批流程。

### 8.1 分支模型

采用 AoneFlow：

- `master` 或 `main`：主干基准代码，分支保护。
- `release`：发布分支，分支保护。
- `dev`：测试分支。
- `feature/*`：功能开发分支。
- `bugfix/*`：缺陷修复分支。
- `hotfix/*`：线上紧急修复分支。

分支流转：

```plaintext
feature/* -> dev -> release -> 预发布 -> Tag -> 生产 -> master
```

约束：

- 禁止直接提交 `master/main/release`。
- 必须通过 MR 合并。
- 至少 1 人 Code Review。
- 分支生命周期结束后删除。
- `release` 需定期同步到功能分支，避免分支漂移。

### 8.2 Commit 规范

格式：

```plaintext
<type>(<scope>): <subject> --<关联资源>
```

示例：

```plaintext
feat(card-draw): 支持抽卡幂等 --task 123
```

常用类型：

- `feat`
- `fix`
- `perf`
- `refactor`
- `test`
- `docs`
- `build`
- `ci`
- `chore`

### 8.3 上线审批

盖娅平台发布流程：

1. 钉钉 OA 发起上线申请。
2. 运维值班人员创建盖娅项目。
3. `dev` 分支上线到盖娅测试环境。
4. `release` 分支上线到预发布环境。
5. 预发布环境验证通过后创建版本号 Tag。
6. `release` 分支上线到生产环境。
7. 上线后将 `release` 合并回 `master/main`。

## 10. 日志、监控与告警

建议记录：

- 扣次数前后状态。

## 11. 压测与验收

### 11.1 目标

支持 50 并发访问，重点验证抽卡写操作一致性。

### 11.2 建议压测场景

1. 50 个不同用户同时访问首页。
2. 50 个不同用户同时抽卡。
3. 10 个用户，每个用户 5 个并发请求同时抽卡。
4. 同一用户连续重复提交同一个 `requestId`。
5. 同一用户连续提交不同 `requestId`，直到次数耗尽。
6. 后台配置查询与 C 端抽卡同时进行。

### 11.3 验收标准

- 不出现负次数。
- 不出现超出可用次数的成功订单。
- 同一 `requestId` 不重复扣次数。
- `draw_order` 与 `draw_order_card` 数量一致。
- 用户卡册 `owned_count` 与订单明细可对账。
- 50 并发下 P95 响应时间建议控制在 300ms 到 800ms。
- 错误率可解释，不能出现事务部分成功。
