# 单词集卡 H5 项目阶段总结与经验沉淀

本文档用于总结本次单词集卡 H5 从页面找回、前端效果恢复、资源接入、轻量化改造、App 对接、埋点验证到 Git 同步过程中形成的经验，供后续类似活动型 H5 或轻量功能验证项目参考。

## 1. 项目背景

本项目最初目标是找回并继续迭代 C 端 H5 页面。由于 Git 上版本不是最新版本，需要根据现有页面和设计素材重新实现近期更新内容，同时满足公司 App 内嵌、测试环境发布、基础数据统计和后续可上线演进的要求。

本阶段重点不是建设完整生产后台，而是在可控范围内完成轻量功能验证：

- H5 页面可以在 App 内正常访问和交互。
- 卡包、抽卡、翻卡、卡册、卡牌详情等核心流程可用。
- 卡牌和卡包资源使用正式设计素材。
- 抽卡规则和卡池配置前端静态化。
- 本地记录每日次数、卡册、抽卡历史，满足测试验证。
- 埋点可被公司统计平台识别。
- 代码可按公司 Git 流程提交测试环境。

## 2. 已完成的主要工作

### 2.1 H5 页面恢复与 Pad/移动端适配

针对页面在 iPad、iPhone 等尺寸下的显示问题，完成了多轮适配：

- 调整页面最大宽度和居中展示规则。
- 修复卡册标题底图在滚动时的遮挡和高度不足问题。
- 修复卡册展开/收起状态宽度不一致问题。
- 优化首页、选择卡包页、开包页、抽卡结果页在不同屏幕下的间距。
- 禁止移动端双指缩放，保持 H5 自动适配屏幕。

经验：

- 活动 H5 一定要尽早用 iPhone、iPad、App WebView 三类场景测试。
- 不要只看桌面浏览器模拟器的默认缩放效果，App 内 WebView 的安全区、原生返回按钮、状态栏高度都会影响布局。
- 卡包、卡牌这类固定比例元素应尽量用稳定宽高、`max-width`、`object-fit` 和父容器居中共同约束。

### 2.2 视觉动效与交互体验

前端实现了多类动效：

- 页面渐变流动背景。
- 首页入口区域扫光。
- 开包动画视频播放。
- 抽卡结果五张卡堆叠和逐张飞出。
- 卡牌详情和抽卡结果大卡的触摸/鼠标倾斜联动。
- SSR/UR 等高稀有卡保留高级动效。
- LR/XR 保留独立高级效果。
- 抽卡结果提示文案“点击任意位置继续”渐隐渐显。

同时根据测试反馈做了体验修正：

- 当前卡牌飞出后，剩余卡牌不再做额外位移动作。
- 抽卡结果页只在展示当前卡牌时自动发声，用户点击不再重复发声。
- 抽卡结果页点击卡牌或空白区域只切换下一张。
- 卡牌文字、翻译区域根据新设计重新排版。

经验：

- 动效要区分“列表态”和“详情态”。列表中大量卡牌同时播放高级动效会影响性能，也会显得杂乱。
- 抽卡结果这种强交互页面，动画状态要特别注意顺序：开包、视频、展示卡堆、切卡、飞出、入册，每一步都要避免数据和动画状态错位。
- App 端性能优先级高于浏览器展示效果，高稀有特效应只在必要的大卡场景启用。

### 2.3 资源替换与正式卡图接入

资源替换分为几类：

- 卡包资源：`/assets/h5/pack`
- 卡牌外框资源：`/assets/h5/card`
- 正式卡面图：`/assets/h5/card-images`

正式卡面图来源于设计导出的分稀有度文件夹，文件命名规则为：

```text
单词_稀有度_数量_min.png
```

实际解析时只使用：

- 单词
- 稀有度

数量和 `min` 忽略。

当前正式卡图已放入代码库静态资源目录：

```text
src/main/resources/static/assets/h5/card-images
```

两份卡池配置均已更新图片路径：

```text
src/main/resources/static/assets/h5/config/card-pool-v1.json
src/main/resources/card-pool/v1.json
```

经验：

- 如果暂时不申请 OSS，图片可以先放进 Spring 静态资源目录，随服务一起发布。
- 不建议把 H5 静态资源放到项目根目录 `uploads`，因为该目录更像运行时上传目录，是否随发布包携带、是否有静态访问映射并不稳定。
- 正式上线如果图片规模继续扩大，仍建议迁移到 OSS/CDN，减少服务包体积并提升缓存能力。

### 2.4 卡池与轻量化方案

项目曾讨论过完整后端、MySQL、管理后台等方案。基于当前阶段是轻量功能验证，最终采用：

- 不做卡牌管理后台。
- 不接 MySQL。
- 卡池和抽卡规则写入静态 JSON 配置。
- 前端读取配置后执行本地抽卡。
- 卡册、每日次数、抽卡历史暂存在 `localStorage`。
- 保留“模拟次日”入口，便于测试每日次数重置。

当前轻量化方案可支持：

- 卡池固定验证。
- 每日免费次数验证。
- 卡册收集流程验证。
- 抽卡历史本地验证。
- 埋点验证。

当前轻量化方案不适合直接承载：

- 真实用户跨设备同步。
- 严格防刷。
- 真实抽卡历史留存。
- 长期活动运营配置。
- 需要审计或客服追溯的数据。

经验：

- 功能验证期可以先用静态配置和本地状态降低成本。
- 一旦进入正式运营，真实卡册、每日次数防刷、跨设备同步、抽卡历史必须回到后端和数据库。
- 技术方案应与项目阶段匹配，不要为了测试项目过早引入完整后台，也不要把验证方案误当生产方案。

## 3. App 内嵌与 JSBridge 经验

本项目接入了公司 App WebView，并尝试处理 H5 关闭按钮、原生返回按钮等问题。

已做工作：

- 引入 `@nat/jsBridge@2.6.0` 对应 JSBridge 脚本。
- H5 关闭按钮尝试调用多个 native close 命令。
- 增加 debug 面板，便于 App 内查看桥接、页面状态和错误日志。
- 尝试 `set_back_button`、`set_header`、`setupFullscreenNativeBackStyle` 等方法。

已验证现象：

- `set_back_button` 无效。
- `set_header` 无效。
- `setupFullscreenNativeBackStyle` 可以影响原生返回按钮样式，但不一定能真正隐藏。
- 加 `"hide": true` 后仍需以 App 实测结果为准。

经验：

- App JSBridge 文档与实际容器行为可能不完全一致，必须真机验证。
- H5 自带关闭按钮是否生效，取决于 App 是否提供可用 close API。
- 原生返回按钮隐藏、透明、样式修改属于 App 容器能力，H5 只能调用协议，不能保证最终效果。
- 接入 App 时应尽早准备 debug 面板，减少“看不到日志”的排查成本。

## 4. 埋点接入与验证

本项目按 `trackify-sdk 3.0.0` 规范重新梳理了 C 端 H5 埋点。

旧方式主要依赖 `pind.js`，需要在业务代码或 DOM 点击逻辑中手动调用 `__sdonclick(value)`。这种方式会让埋点和业务交互耦合在一起，后续新增、修改、排查事件成本较高。

本次调整后的原则是：

- 使用 `trackify_3.0.0.js` 作为统一埋点 SDK。
- 事件类型 `t` 固定为 `card.000001`。
- 公共业务参数统一写入 `window.__m_static_jsv.p`。
- 普通点击事件优先通过 `data-analytics` 无痕采集。
- 页面访问、流程状态、开包成功等非 DOM 点击行为通过 `trackCardEvent` 手动上报。
- 业务代码只负责触发业务状态变化，埋点参数尽量集中封装。

`trackify-sdk 3.0.0` 是精简版能力，本期只使用：

- PV/UV 页面访问统计。
- OC 点击埋点。
- 手动事件上报。

不依赖性能、异常、滚动、表单、曝光、视频、unload 等自动采集能力。

当前公共参数结构：

```json
{
  "t": "card.000001",
  "p": {
    "project": "card_tcg",
    "page_name": "word_card_h5",
    "unitid": "...",
    "userId": "...",
    "poolVersion": "..."
  }
}
```

对应最终上报结构会被 SDK 合并为类似：

```json
{
  "t": "card.000001",
  "v": {
    "project": "card_tcg",
    "page_name": "word_card_h5",
    "unitid": "...",
    "userId": "...",
    "poolVersion": "...",
    "action": "PG_CARD_MAIN"
  }
}
```

当前实现方式：

- 页面头部初始化 `window.__m_static_jsv`，用于 SDK 读取公共参数。
- `buildTrackParams` 统一生成 `project`、`page_name`、`unitid`、`userId`、`poolVersion` 等字段。
- `syncTrackifyParams` 在页面切换、卡池变化时同步更新公共参数。
- `analyticsAttr(action, extra)` 统一生成 `data-analytics`，用于按钮和卡牌点击。
- `trackCardEvent(action, extra)` 负责手动上报页面访问和关键流程事件。

当前主要事件包括：

- `PG_CARD_MAIN`
- `CK_CARD_MAIN_DRAW`
- `CK_CARD_MAIN_PACK`
- `CK_CARD_PACK_SELECT`
- `CK_CARD_PACK_OPEN`
- `OC_CARD_PACK_OPEN_SUCCESS`
- `PG_CARD_RESULT_FLIP`
- `CK_CARD_RESULT_NEXT`
- `PG_CARD_RESULT_FINAL`
- `CK_CARD_RESULT_SAVE_ALBUM`
- `PG_CARD_COLLECTION`
- `PG_CARD_DETAIL`

事件命名约定：

- `PG_`：页面访问或页面阶段曝光。
- `CK_`：用户点击行为。
- `OC_`：关键业务操作完成结果。
- 事件名由项目侧定义，保持语义清晰即可。

验证结论：

- `topic = card.000001` 可被统计平台识别。
- `action` 可解析。
- `value.v` 中可看到 `project`、`page_name`、`unitid`、`userId`、`poolVersion` 等字段。
- `uuid` 可用于匿名 UV。
- 平台外层 `userid` 字段当前可能为 `0`，不应直接依赖。

已在公司查询平台中验证到数据落库：

- `topic` 显示为 `card.000001`。
- `action` 显示为 `PG_CARD_MAIN` 等事件名。
- `value` 中包含完整 JSON。
- `uuid` 有值，可支撑匿名用户去重。
- `userid` 列为 `0` 时，仍可从 `value.v.userId` 或 `value.v.unitid` 取业务用户标识。

建议统计口径：

- PV：按 `action` 或页面事件统计。
- 点击：按 `action` 统计。
- 匿名 UV：按 `uuid` 去重。
- 业务用户 UV：优先按 `value.v.userId` 或 `value.v.unitid` 去重。

示例口径：

```sql
-- 匿名 UV
count(distinct uuid)

-- 业务用户 UV
count(distinct json_extract(value, '$.v.userId'))
-- 或
count(distinct json_extract(value, '$.v.unitid'))
```

经验：

- 埋点是否“可用”，不只看请求是否发出，还要看数据平台是否能解析 `t`、`action`、`value`。
- `trackify-sdk 3.0.0` 更适合本期这种轻量 H5，不需要额外接入复杂自动采集。
- 点击事件优先写 `data-analytics`，减少业务代码中的手动埋点。
- 页面访问、抽卡成功、结果页曝光等不是简单 DOM 点击的事件，仍应手动上报。
- 如果 App 不能传真实用户 ID，仍可统计匿名 UV，但业务用户 UV 会不准。
- 若公司数据侧可以从 cookie 解析用户，要确认埋点请求是否携带 App WebView 内 cookie。
- 最稳方案是 App 打开 H5 时拼接 `unitid/userId`。

## 5. Git 与发布流程经验

本项目使用公司 Git：

```text
https://flow.51talk.biz/git/card_tcg/card.git
```

当前开发分支：

```text
card-draw-prototype
```

推送过程中遇到过远端 ahead，本地 push 被拒绝的问题。推荐流程：

```bash
git pull --rebase origin card-draw-prototype
git push origin card-draw-prototype
```

如果本地有不相关改动，应只提交本次相关文件，避免误带。

本项目曾长期存在以下本地未处理资源，后续已确认不再需要并删除：

```text
src/main/resources/static/assets/h5/card/back.png
src/main/resources/static/assets/h5/card/frame-nr.png
uploads/card-draw/images/20260603/
```

类似情况后续仍需注意：删除资源前先确认是否仍有代码引用，确认后再删除并清理引用，避免上线静态资源检查报缺失。

经验：

- 每次提交前先看 `git status`。
- 不要使用 `git add .`，尤其项目里有资源目录、上传目录、删除项时。
- 删除文件必须先确认。
- 二进制资源变更多时，提交信息要写清楚资源范围。

## 6. 推荐的后续演进路径

### 6.1 当前阶段可以继续使用的方案

适用于测试和功能验证：

- 静态 JSON 卡池配置。
- H5 本地抽卡。
- `localStorage` 存储卡册和次数。
- 图片随代码发布。
- 埋点统计行为数据。

### 6.2 正式上线前建议补齐

如果要进入正式活动运营，建议补齐：

- 后端抽卡接口。
- 服务端每日次数控制。
- 服务端卡册记录。
- 服务端抽卡历史。
- 用户身份接入。
- 防刷策略。
- OSS/CDN 图片资源。
- 管理端或配置发布流程。
- 数据看板和异常监控。

### 6.3 是否必须使用 Java/MySQL

不一定必须使用 Java，但正式运营必须有服务端状态存储。可选方案：

- Node.js + MySQL：比 Java 轻，适合小型活动。
- Serverless + 数据库：部署轻，但需确认公司运维是否支持。
- Java + MySQL：公司标准化程度高，但对测试项目偏重。
- 纯前端：只适合验证，不适合真实运营。

## 7. 后续类似项目建议流程

建议按以下顺序推进：

1. 明确项目阶段：验证、灰度、正式运营。
2. 先确定数据是否需要真实留存。
3. 再确定是否需要后端和数据库。
4. 尽早确认 App WebView 能力，包括关闭、返回、状态栏、安全区。
5. 确认埋点 SDK、事件规范和用户 ID 获取方式。
6. 前端先完成主流程闭环，再做高级动效。
7. 资源目录和命名规则提前约定。
8. 使用真机、iPad、App 内环境做布局验证。
9. 每轮提交只提交本轮相关文件。
10. 上线前补齐资源托管、缓存、统计、回滚方案。

## 8. 本次关键教训

- 找回页面后，不能只补代码，要同步梳理资源、配置、缓存和运行环境。
- 旧占位图问题不一定是资源没替换，也可能是代码里强制使用占位图。
- App 内问题不能完全依赖文档判断，要靠真机和 debug 面板确认。
- 轻量化方案可以显著降低验证成本，但边界必须写清楚。
- 埋点能否统计 UV，核心取决于是否有稳定用户标识；没有业务用户 ID 时只能做匿名 UV。
- 图片先放代码库是可行的，但长期看 OSS/CDN 更适合正式运营。
